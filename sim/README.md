# fast_road — точное ускорение highway-env 1.12.1

Время шага highway-env растёт почти квадратично с числом автомобилей: на каждом кадре каждый
автомобиль IDM/MOBIL перебирает всех остальных в поиске соседей (`Road.neighbour_vehicles`),
а проверка столкновений перебирает все пары (`Road.step`). `fast_road` убирает эти переборы,
не меняя результата.

* **Соседи.** Раз в кадр позиции всех автомобилей проецируются на полосы и сортируются (NumPy).
  При запросе проверяются только ближайшие кандидаты, и проверяются исходным кодом highway-env:
  `local_coordinates`, `on_lane(margin=1)`, те же сравнения и тот же выбор при равенстве (порядок
  списка). Остальные автомобили отсекаются с запасом 1e-6 м, а ошибка векторного расчёта ~1e-11 м,
  поэтому изменить ответ они не могут.
* **Столкновения.** Векторные предфильтры пар: тот же сферический тест, что в `_is_colliding`
  (запас 1e-3 м), и тест разделяющих осей по нормалям сторон прямоугольников с учётом смещения за
  `dt` (запас 1e-4 м). Для отброшенных пар исходный код вернул бы «нет контакта» и ничего бы не
  изменил. Оставшиеся пары проходят исходный `handle_collisions` в исходном порядке (i, j).

Штатный код используется автоматически, если: есть `road.objects`; включён
`neighbour_vehicles_connected_lanes`; полоса не `StraightLane`; класс автомобиля переопределяет
`handle_collisions`, `_is_colliding`, `polygon`, `direction` или `velocity`; поиск соседей
вызывается вне `Road.act` (например, из фильтра).

## Подключение

```python
from sim import fast_road
fast_road.enable()   # до первого шага, в КАЖДОМ процессе; проверяет highway-env == 1.12.1
```

На macOS `multiprocessing` и `SubprocVecEnv` запускают воркеры через spawn. Вызывайте `enable()`
при импорте модуля, который создаёт среду, иначе воркеры останутся на штатном коде.

## Проверка эквивалентности

Из корня репозитория:

```bash
python -m pytest -q sim/test_fast_road.py                     # короткий набор, 3–5 мин
FAST_ROAD_FULL=1 python -m pytest -q sim/test_fast_road.py    # полный набор, 15–20 мин
```

Штатный и ускоренный код запускаются в разных процессах. После каждого кадра побитово
сравнивается состояние всех автомобилей: позиция, курс, скорость, действие, `impact`, `crashed`,
`lane_index`, `target_lane_index`, `timer`, `target_speed`. На каждом шаге сравниваются также
наблюдение, награда и решение фильтра. Сценарии: основной генератор протокола с D = 10/25/40
(`experiments/generator.py`, раздел 7.6), включая кадры `reset()` (прогрев 20 с без ego, вставка)
и рециркуляцию окна; штатный highway-v0 с плотным потоком (N = 100/160); эпизоды с RSS-фильтром
на основном генераторе. После столкновений моделирование продолжается. Короткий набор: 6 эпизодов,
460 шагов, 1 920 кадров, из них 1 000 — кадры `reset()`.

Результат полного набора v10 на упрощённом генераторе `window_env.py`: 24 эпизода, 2 700 шагов,
5 400 кадров, 484 600 состояний автомобилей, 202 столкновения фоновых автомобилей, 17 перехватов —
расхождений 0. Результат на основном генераторе даёт CI (`verify.yml`, шаг «Check sim equivalence»).

Тест переведён на основной генератор; `window_env.py` оставлен как упрощённая копия, на которой
сделан замер v10 ниже. Тест нужно прогнать на каждой машине, где идёт счёт: побитовая воспроизводимость между x86 и Apple Silicon не гарантируется
даже для штатного кода, поэтому каждый запуск (ячейка × сид) считается целиком на одной машине,
а машина записывается в лог.

## Замер v10 (`window_env.py`; Linux x86-64, Xeon 2.9 ГГц, один процесс; мс на шаг решения = 2 кадра)

| D (авт. в окне) | штатно | fast_road | ускорение | фильтр, `decide()` |
|---|---:|---:|---:|---:|
| 10 (40)  | 37–40   | 18–19 | ×2.1     | 6–7   |
| 25 (100) | 150–166 | 32    | ×4.7–5.3 | 8–9   |
| 40 (160) | 350–413 | 49–54 | ×6.5–8.4 | 10–11 |

`python sim/bench.py orig` и `python sim/bench.py fast` повторяют замер на основном генераторе
и дополнительно измеряют `reset()` (расстановка, прогрев, вставка); запустите их на каждой машине
счёта. Замер CI для `fast` публикуется в комментарии пилота к PR.

## Дальше (не сделано)

Остальное время — линейная по N работа самой модели IDM: `np.clip`, `local_coordinates`,
`get_closest_lane_index`. В фильтре ~40 % времени занимает `_NeighbourPrediction.at(n)`: она
каждый раз пересчитывает траекторию с нуля. Если один раз запомнить ряд x, v (те же операции
в том же порядке), результат не изменится, а фильтр ускорится примерно в 1.5 раза.
