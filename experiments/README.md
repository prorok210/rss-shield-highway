# Эксперименты

Код экспериментов протокола: основной генератор трафика, 86-признаковое наблюдение,
semi-MDP-переходы с накоплением наград при перехвате, DQN, счётчики раздела 7.7 и короткий
сквозной пилот цепочки обучения (раздел 8). Подтверждение H1–H3 на этом этапе не выполняется.

| Модуль | Содержание |
|---|---|
| `generator.py` | `ProtocolHighwayEnv` (основной генератор; доступен как `experiments.ProtocolHighwayEnv` и под идентификатором gymnasium `rss-protocol-highway-v0`): 4 полосы, окно трафика плотности D (раздел 7.6): расстановка, прогрев 20 с без ego, рециркуляция окна, вставка ego (не более 2 удалений), признаки небезопасного старта по ρ; наблюдение из 86 признаков (75 кинематических + команда в FIFO + brake_mode + целевая скорость + целевая − текущая полоса); сохранение и восстановление стартового состояния |
| `env.py` | единственное место создания среды; при импорте включает `fast_road` (`RSS_FAST_ROAD=0` выключает); кэш стартовых состояний `start_states/D{D}_seed{seed}.pkl` |
| `h1.py` | единое определение события и корректного старта H1 (п. 6, 7.6, 7.7 протокола): правило старта при ρ = 1.0 с для всех плеч, ρ классификации плеча (ρ фильтра; ρref = 1.0 с без фильтра, в том числе Baseline 2), операциональная классификация столкновения по покадровой записи (`classify_collision`), событие H1, сводка `h1_summary` с CR_total отдельно от категорий |
| `rewards.py` | награды R_v и R_S (раздел 2) |
| `dqn.py` | DQN на NumPy: 2×256 ReLU, Adam, функция потерь Хьюбера, целевая сеть, цель с максимумом по A_safe(s′); буфер (s, a, R, s′, d, n, маска(s′)); сохранение и загрузка `.npz` |
| `runner.py` | эпизод с фильтром: шаги политики и перехвата, сборка semi-MDP-переходов, счётчики E, N_att, N_blocked, N_att_int, N_exec, N_exec_int, R_int, BLCR, BLCR_rss (без блокировок busy и «нет полосы»: N_busy, N_no_lane), v_eff, JerkRMS; множество решений (шаги политики и перехвата, E, N_att, N_blocked, N_att_int) задано один раз в `rss_shield/accounting.py`; журнал шагов со статусами `policy_step`, `intervention`, `sup_cmd`, `block_reason`, `active_cmd`, `active_sup`, `brake_mode`, `return_active`, `fallback`, `abort_ignored` (те же имена, что в журнале `rss_shield/sim.py`) |
| `pilot.py` | пилот (фильтр — только в конфигурации `MAIN_SERIES`; фактическая конфигурация каждого эпизода пишется в счётчики `shield_cfg` / `main_series`, и пилот не проходит, если она другая; в конце печатаются итоговые счётчики п. 7.7 по каждому плечу): прогрев, стартовые состояния, обучение, записи буфера до, во время и после перехвата, сохранение и загрузка модели, оценочный эпизод, итоговые счётчики, искатель перестроений (исполненные смены полосы и ABORT на основном генераторе при ρ = 0.1 и 0.6 с), диагностика бокового порога, доля тактов с допустимой сменой полосы по сетке D × ρ для четырёх конфигураций маски с причинами блокировки; отчёт `report.md` |
| `stats_pilot.py` | статистический пилот: таблица эпизодов по сетке D × ρ для Режимов А и Б и для плеча Baseline 2 (общие сиды эпизодов 900 300–900 303; политики без обучения) — вход для `python -m analysis.run`; зафиксированный прогон — `runs/pilot_run/stats/` |
| `tests/` | 12 тестов правил H1 (`test_h1_rules.py`: граничные случаи события и старта для обоих плеч, порядок правил классификации), 13 тестов цепочки (включая проверку окна трафика по границе зоны п. 7.4 и огибающей скоростей) и регрессионный тест учёта смен полосы (`test_lane_change_accounting.py`: ego в крайней полосе, политика чередует смены полосы наружу и внутрь; 2 случая — правая и левая крайняя полоса) |

Тип шага (политики или перехвата) задаётся тактом решения, а не командой, активной в течение шага.
Пересечение разметки (N_exec) относится к шагу решения, чья команда действительно изменила
`target_lane_index`. `vehicle.py` исполняет LANE_LEFT/RIGHT от целевой полосы в момент выхода команды
из FIFO, поэтому `runner.py` открывает запись манёвра, когда команда сдвигает целевую полосу от
текущей, и запоминает номер шага решения, на котором команда выдана. Если до пересечения целевая
полоса возвращается к текущей (разворот противоположной командой, ABORT или FALLBACK), запись
снимается. Пересечение берёт самую раннюю открытую запись своего направления (столбец
`exec_from` журнала); пересечение без записи считается в N_exec_other (ожидается 0). Супервизорные
команды смену полосы не начинают (TAKEOVER сохраняет боковую цель уже начатого манёвра, ABORT
предлагается только до пересечения разметки, FALLBACK удерживает полосу, в которой находится центр
ego). Поэтому N_exec считается на той же экспозиции E, что и N_att; N_exec_int — пересечения,
физически пришедшиеся на активную супервизорную команду, — приводится отдельно и входит в N_exec.

DQN написан на NumPy, поэтому зависимости обучения совпадают с `requirements.txt`; отдельный
`requirements-train.txt` не нужен. Градиенты проверяются конечными разностями в тестах.

## Статистический план на данных пилота

```bash
python -m experiments.stats_pilot --out runs/pilot_run/stats
python -m analysis.run --episodes runs/pilot_run/stats/episodes.csv --out runs/pilot_run/stats --boot 199 --boot-sens 999 --boot-diff 2000
python -m analysis.power --starts runs/pilot_run/start_states.csv | awk '/^# Power of H1a/{n++} n==2' > runs/pilot_run/stats/power.md
```

Политики статистического пилота не обучаются, поэтому `analysis.md` показывает только, что каждый шаг плана вычисляется.
`analysis.power` за один запуск печатает два отчёта подряд: для номинального плана (каждый старт корректен) и для доли
корректных стартов пилота. В `power.md` хранится только второй; он основной, потому что опирается на стартовые состояния пилота.

## Запуск

Из корня репозитория:

```bash
python -m pytest -q experiments/tests
python -m experiments.pilot --out runs/pilot_local            # пилот раздела 8
python -m experiments.pilot --out runs/pilot_quick --quick    # укороченный вариант для отладки
```

В CI пилот запускает `.github/workflows/pilot.yml`; `report.md` и остальные файлы пилота — в артефакте запуска. Модели `.npz` в git не кладутся. Если запуск CI не состоялся,
те же шаги `pilot.yml` (замер шага, тесты, пилот) выполняются локально: `python sim/bench.py fast 40`,
`python -m pytest -q experiments/tests analysis/tests`, `python -m experiments.pilot --out runs/pilot_run` (зафиксированный прогон — `runs/pilot_run/`).

## Требования к коду экспериментов

1. Среда создаётся только в `env.py`, и при его импорте вызывается `from sim import fast_road; fast_road.enable()`. Так ускорение включено в каждом процессе, включая воркеры, которые macOS запускает через spawn.
2. Состояние на момент вставки ego (после прогрева) для валидации, dev и теста рассчитывается один раз на пару (D, сид). Оно сохраняется в `start_states/` вместе с состоянием генератора случайных чисел и переиспользуется всеми политиками, ρ и режимами (`env.reset_cached`). Тест `test_start_state_cache_is_bit_identical`: эпизод из сохранённого состояния побитово совпадает с эпизодом, посчитанным с нуля.
3. Счёт — очередь независимых задач (запуск обучения или блок эпизодов ячейки), по процессу на ядро. В каждом процессе один поток: `OMP_NUM_THREADS=1`, `MKL_NUM_THREADS=1`, `OPENBLAS_NUM_THREADS=1`, `VECLIB_MAXIMUM_THREADS=1` (пилот задаёт их сам до импорта NumPy). При перезапуске готовые задачи пропускаются. На macOS очередь запускается через `caffeinate -i`. Очередь задач основной серии ещё не реализована: пилот выполняется одним процессом, запускатель серии появится вместе с её конфигурациями.
4. Каждая задача выполняется целиком на одной машине. В её журнал пишутся машина, ОС, модель CPU, версии пакетов и хэш коммита (`journal.md` пилота).
5. До счёта на каждой машине выполняются `python -m pytest -q sim/test_fast_road.py` и `python sim/bench.py fast`; время шага идёт в раздел 8 протокола. Тест эквивалентности выполняется на основном генераторе (`generator.py`), упрощённый `sim/window_env.py` для него больше не используется.
